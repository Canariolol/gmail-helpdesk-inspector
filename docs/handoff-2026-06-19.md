## 1. Objetivo

El sistema nació como app interna para `catherine.trivino@west-ingenieria.cl` (ya en Firestore) y fue evolucionando hacia un modelo SaaS (organización, roles, gating de setup, rate limits). Se busca:

1. Que el **usuario interno conserve acceso total** (sin rate limits, sin gating de setup, sin futuros paywalls), mientras el resto puede ir hacia SaaS.
2. **Mejorar la precisión** de clasificación válido / no-válido / "para revisión" (había inconsistencias).
3. Usar la **API de Gmail** para traer **etiquetas/bandejas** (y más metadata útil) y que el usuario elija qué incluir/omitir — obtenido **al conectar la cuenta**, no al pulsar "Analizar".
4. **Guardar la configuración de filtros** (presets), para no reingresarla cada vez y poder alternar tipos de hilos.

**Decisiones tomadas con el dueño:** roadmap por fases; cuenta privilegiada vía **allowlist por env var**; palanca de precisión = **IA + heurísticas + etiquetas**; selección de etiquetas **incluir + excluir** (default = comportamiento histórico); además **presets guardados**.

**Hallazgo clave:** `gmail.readonly` (scope ya consentido) **ya cubre** leer etiquetas, perfil, alias (`settings.sendAs`) y filtros (`settings.filters`). **No hace falta ampliar scope ni re-consentir.**

Costura única `AppConfig::is_privileged_account(email)` alimentada por env var `INTERNAL_FULL_ACCESS_EMAILS`.

- `apps/api/src/config/mod.rs`: campo `internal_full_access_emails` + helper `is_privileged_account` (+ test unitario).

- `apps/api/src/policies.rs`: flag `account_unrestricted` en `OrgConfigResponse`.

- **Invariante:** el bypass solo relaja cuotas/setup/consentimiento; **nunca** toca el aislamiento de sesión/propiedad (`require_session`, `require_owned_thread`).

### 3C — Endurecer heurísticas determinísticas

**Objetivo:** menos falsos válidos/no-válidos en la primera pasada (antes de IA), para que la IA y la revisión manual reciban menos ruido.

Sub-tareas concretas:

1. **`ignored_keywords` en heurística → YA HECHO.** Verificar y no rehacer: `classify_thread` ya llama `subject_has_ignored_keyword(&lower_subject, &config.ignored_keywords)` (`analysis/mod.rs`, dentro del bloque que setea `noise`). El comentario antiguo de "no se usa" quedó desactualizado.

2. **Usar `valid_request_criteria` / `non_responsibility_rules` también en heurística** (hoy **solo** alimentan a la IA, en `audit_thread::AiWorkerPolicyContext`). 
   - **Restricción arquitectónica importante:** `classify_thread(run_id, gmail_thread_id, messages, config: &AnalysisConfig)` recibe `AnalysisConfig`, que **no** contiene esos campos (viven en `AnalysisPolicy`/`PolicySnapshot`). Para usarlos hay dos caminos:
     - (a) Pasar el `PolicySnapshot` (o solo esos `Vec<String>`) a `classify_thread` como parámetro nuevo → cambia su firma y **todos** los call sites de test (`analysis/mod.rs` tests: ~6 llamadas, más `process_one_thread` en `http/mod.rs`).
     - (b) Hacer el ajuste como **paso de refinamiento posterior** (igual que se hizo con las etiquetas: ver `refine_classification_with_gmail_labels`), recibiendo los criterios como `&[String]` y aplicándolos en `process_one_thread` después de `classify_thread`. **Recomendado (b)**: menor churn, no rompe los tests de `classify_thread`.
   - Implementación sugerida (b): una fn `refine_classification_with_policy_hints(thread: &mut EmailThread, subject/snippets, non_responsibility_rules: &[String])` que, ante coincidencia clara de una regla de no-responsabilidad en asunto/remitente, enrute a revisión (no invertir a ciegas). Mantener conservador.

3. **Umbral de "forma sospechosa".** Hoy en `classify_thread`:
   ```rust
   let suspicious = messages.len() >= 8 || messages.iter().filter(|m| m.is_external).count() >= 4;
   ```
   Es un umbral duro. Propuesta: ponderar por tiempo de respuesta/antigüedad (un hilo largo pero resuelto rápido no debería ser "sospechoso"). **Riesgo:** afecta `classification` y `manual_review_required` → puede romper tests en `analysis/mod.rs` (ej. los que esperan `ValidClientRequest`/`manual_review`). Ajustar y correr `cargo test`.

4. **Allowlist de remitentes "automáticos" de confianza** para reducir falsos `Automated`. Hoy `is_automated_sender(email, headers)` (`analysis/mod.rs`) usa patrones anclados de local-part (`no-reply`, `noreply`, etc.) + header `auto-submitted`.
   - Se invoca desde `gmail/mod.rs::normalize_message`, que **sí** tiene `config: &AnalysisConfig`.
   - Para una allowlist configurable habría que: agregar un campo (ej. `trusted_sender_domains`) a `AnalysisConfig` (**ojo: mismo patrón de ~12 literales que `include_labels`**) y a `AnalysisPolicy`, pasarlo a `is_automated_sender`, y exceptuar esos dominios. Alternativa más barata: allowlist por **constante** en código (sin config) si no se necesita por-tenant.

### 3D — Muestreo de auditoría estratificado

**Objetivo:** auditar con IA una fracción mayor de los `Ambiguous`/dudosos y una menor de los `ValidClientRequest` claros, para cazar inconsistencias válido/no-válido (hoy el muestreo es plano: 1 de cada 10).

**Cómo funciona hoy:**
- `execute_analysis` (`http/mod.rs`) calcula `excluded_sample_ids(&thread_ids)` **antes** de clasificar:
  ```rust
  fn excluded_sample_ids(ids: &[String]) -> Vec<String> {
      ids.iter().enumerate().filter(|(i, _)| i % 10 == 0).map(...)...
  }
  ```
- En `process_one_thread`, tras clasificar:
  ```rust
  let should_audit = ai_enabled && received_human_thread
      && (thread.is_valid_client_request
          || thread.manual_review_required
          || processing.excluded_sample.contains(&thread.gmail_thread_id));
  ```

**Restricción clave:** el muestreo actual es **pre-clasificación**, así que no se puede estratificar por `classification` en `excluded_sample_ids`. La clasificación recién existe dentro de `process_one_thread`.

**Enfoque recomendado:** mover la decisión de muestreo a **dentro de `process_one_thread`**, después de `classify_thread` (+ refinamientos), reemplazando el `excluded_sample.contains(...)` por una decisión estratificada determinística. Ejemplo:
```rust
// sampling determinístico por hash del gmail_thread_id (sin estado aleatorio):
fn sample_bucket(thread_id: &str) -> u8 { /* p.ej. (hash % 100) */ }
let sample_rate = match thread.classification {
    Classification::Ambiguous => 100,            // siempre
    Classification::ValidClientRequest => 20,    // 20%
    _ => 5,                                       // 5%
};
let in_sample = sample_bucket(&thread.gmail_thread_id) < sample_rate;
let should_audit = ai_enabled && received_human_thread
    && (thread.is_valid_client_request || thread.manual_review_required || in_sample);
```
- Determinístico (hash del id) para reproducibilidad; el repo ya depende de `rand` si se prefiere aleatorio, pero **mejor determinístico**.
- Se puede borrar `excluded_sample_ids` / `ThreadProcessingContext.excluded_sample` o dejarlos para otro uso.
- **Riesgo bajo de tests** (no hay test que fije el muestreo), pero validar que `process_one_thread` siga compilando y que el conteo de tokens IA no se dispare.
